From GPU to served model

One chain of reasoning: every section exists because the previous one created a problem. Everything here is interactive.

1. Why a GPU at all?

  • Challenge: a neural network is mostly matrix multiplication, which means millions of tiny, independent multiply-adds.
  • Why does that matter? Independent work does not need to wait for other work, so it can all run at once.
  • Who can run thousands of things at once? A CPU has a few strong cores (great at complex sequential logic). An NVIDIA GPU has thousands of simple cores (great at doing the same operation on lots of data).
  • So: we hand the GPU the math. Race them below: 256 independent tasks.

2. CUDA: how do we tell thousands of cores what to do?

  • Challenge: we cannot write 10,000 separate programs.
  • Idea: write one function (a kernel) and run it on many threads. Each thread must know which element is its own.
  • How does a thread know? Threads are grouped into blocks, blocks into a grid. Each thread computes i = blockIdx*blockDim + threadIdx.
  • So: C[i] = A[i] + B[i] runs for all i simultaneously. CUDA is NVIDIA's platform (language extensions, compiler, libraries) for this model. Click a thread, then launch.
__global__ void add(float*A,float*B,float*C){
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  C[i] = A[i] + B[i];
}  // launched as add<<<3, 4>>>(A,B,C)

3. NVIDIA Container Toolkit: GPUs inside containers

  • Challenge: we ship apps in containers for portability, but a GPU is a physical device with a kernel driver on the host.
  • Can the image contain the driver? No. The driver must match the host kernel, and a container shares the host kernel.
  • So who connects them? A runtime hook that, at container start, injects the device files and driver libraries from the host.
  • Result: the image holds only CUDA user libs plus your app and stays portable. Step through it.

4. Kubernetes: scheduling GPUs across machines

  • Challenge: Kubernetes knows CPU and memory natively, but nothing about GPUs.
  • How can it learn? A device plugin (a DaemonSet per node) discovers GPUs and tells the kubelet: "this node has 4 nvidia.com/gpu".
  • How does a pod ask for one? Under resources.limits. For extended resources, requests must equal limits, and only whole numbers are allowed (no 0.5 GPU).
  • So: the scheduler just counts free GPUs per node, and a pod that fits nowhere stays Pending. Try it.

5. VRAM and GPU utilization

  • Challenge: the pod got a GPU. Will our model fit on it?
  • What must live in VRAM? The weights (params × bytes each), the KV cache (the attention memory of every token of every request in flight), and some overhead.
  • What happens if the total exceeds VRAM? Out-of-memory. There is no swap to save you.
  • Note: "utilization" in nvidia-smi only means a kernel was running during the sample window, not that the cores were busy. Memory used and utilization are separate numbers. Change the knobs.

6. Quantization: making the weights smaller

  • Challenge: 70B at FP16 is 140 GB, which exceeds one GPU.
  • What costs the memory? Bytes per weight. Do we need 16 bits of precision for each?
  • Not really. Weights cluster in a narrow range, so map them onto fewer levels: q = round((w-min)/scale), and later w ≈ q*scale+min.
  • Trade-off: fewer bits means a smaller model and less memory traffic, but more rounding error. Drag the bits (outline = original, green = quantized).

7. Latency vs throughput, and batching

  • Challenge: generating one token means reading all the weights from VRAM, and that read dominates the time.
  • What if 8 requests share that read? The same weights are loaded once, and each adds only a little extra math.
  • So a bigger batch means more tokens per second overall. But every request now waits for a slightly longer step, which is worse latency for each user.
  • Hence the trade-off: throughput up, per-user latency up. Past the compute limit, a bigger batch only adds delay. Slide it.

8. Model serving: vLLM and Triton

  • Challenge: requests arrive at random times and finish at different lengths. Static batching waits for the slowest request, so finished slots sit idle.
  • Fix: continuous batching. The moment one request finishes, a waiting one takes its slot. Watch both below.
  • New problem: the KV cache grows unpredictably, and reserving max length per request wastes VRAM. vLLM's PagedAttention stores it in small fixed blocks, like OS memory pages, allocated on demand.
  • Where does Triton fit? Triton Inference Server is a general model server: many frameworks (TensorRT, ONNX, PyTorch), HTTP/gRPC endpoints, dynamic batching, and multiple model instances per GPU. vLLM is specialised for LLM generation. Use Triton for a mixed fleet of models, vLLM for LLM throughput (or vLLM as a Triton backend).

Chain recap: matrix math is parallel → GPU + CUDA → container needs host driver (Toolkit) → Kubernetes counts GPUs (device plugin) → model must fit VRAM → quantize → batch for throughput → continuous batching and paging (vLLM/Triton) keep the GPU busy.
